# Что передать бэкенд-разработчикам

Аудит выполнен по коду `project-edesc` на базе коммита `8c7baff` и HTML-макету IdeaHub. Ниже отдельно отмечены существующие контракты и предлагаемые доработки. Предлагаемые маршруты пока не реализованы и не вызываются фронтендом.

## Уже подключено

Фронт: `frontend/`, TypeScript + React + Vite. Все запросы идут на `/api` того же origin; dev-сервер проксирует их на `http://localhost:5000`. Используются Identity cookies (`POST /api/Users/login?useCookies=true`), токены и пароли в localStorage не сохраняются.

| Возможность | Существующий контракт |
| --- | --- |
| Вход, регистрация, выход | Identity API в `/api/Users`, logout с JSON `{}` |
| Восстановление пароля | `/api/Users/forgotPassword`, `/api/Users/resetPassword`; нужна работающая отправка писем |
| Предложения | GET/POST `/api/Suggestions/`; создание возвращает GUID черновика |
| Отправка черновика | POST `/api/Suggestions/{id}/submit` |
| Решение руководителя | POST `.../{id}/approve` с `{regNumber}`; POST `.../{id}/return` с `{reason}` |
| Подразделения | GET/POST `/api/Departments/`, PUT/DELETE `/api/Departments/{id}` |
| Шаблоны | GET/POST `/api/Templates/`, PUT `/api/Templates/{id}`, PATCH `.../{id}/archive` |

JSON enum — строки, как настроено `JsonStringEnumConverter`: статусы `Draft`, `Submitted`, `ReturnedByManager`, `InCommission`, `RevisionRequired`, `Rejected`, `ApprovedPlanning`, `InImplementation`, `Implemented`; типы шаблона `Template` / `Bottleneck`.

В этой ветке добавлен **GET `/api/Users/me`** с RequireAuthorization. Ответ: `{id,email,fullName,position,departmentId,roles}`. Он нужен для восстановления сессии и отображения прав. Это единственная доработка C# в рамках фронтенда; сборку и запуск нужно подтвердить с .NET SDK 10.0.402.

## Приоритет 1 — блокирует полноценный рабочий процесс

### 1. Карточка и принадлежность предложения

Сейчас `SuggestionDto` содержит только `id`, `title`, `status`, `created`; GET по ID отсутствует. Нужны:

- GET `/api/Suggestions/{id}`: `currentFlaws`, `proposedSolution`, `improvementObject`, `targetDepartmentId`, `templateId`, `createdBy`, доступное отображаемое имя автора, `registrationNumber`, `commissionNote`, сроки, ожидаемый и фактический результат, финансовые поля и история переходов.
- Список: добавить как минимум `createdBy`, подразделение, краткое описание и разрешённые действия (`allowedActions` либо согласованная матрица прав).
- Отдельная выборка своих предложений (например, `?scope=mine`), фильтрация доступных данных на сервере. Сейчас обработчик GET возвращает все предложения без фильтра пользователя.
- PUT/PATCH для изменения своего черновика/возвращённого предложения. Сейчас редактировать и исправлять возвращённую идею невозможно.

До появления этих контрактов фронт показывает общий список доступных API записей и краткую карточку. Он не называет этот список «Мои предложения», не выдумывает авторов/описания и не предоставляет редактирование или отправку чужих черновиков. Отправка доступна сразу после создания, с повтором по уже полученному ID при ошибке.

### 2. Проверки прав на сервере

Нужно проверить и закрепить тестами:

- `SubmitSuggestionCommandHandler` выбирает запись только по ID; проверки владельца нет. Сотрудник не должен отправлять чужую запись.
- `GetSuggestionsQueryHandler` возвращает все записи, включая черновики. Определить правила публичной доски, свои записи и видимость руководителю своего подразделения.
- Approve/return имеют `[Authorize(Roles = "AdminL1,AdminL2")]`, но обработчики не ограничивают подразделение руководителя. Согласовать, какие записи может обрабатывать каждая роль.
- Update/Delete подразделений и Update/Archive шаблонов сейчас защищены общей авторизацией endpoint-группы; соответствующие команды не имеют административного `[Authorize]`. Сотрудник может обращаться к ним напрямую, даже если кнопки спрятаны на фронте.
- Матрица `User`, `AdminL1`, `AdminL2`: их соответствие сотруднику, администратору и главному администратору из макета пока не определено. Фронт предоставляет обеим Admin-ролям доступные административные операции; это нужно согласовать.
- При регистрации Identity не назначает роль `User` и не принимает ФИО/должность/подразделение. Обычный авторизованный аккаунт без роли фронт отображает как сотрудника; сервер должен определить политику назначения роли.

### 3. Цикл работы комиссии и внедрения

В enum 9 статусов, но HTTP API умеет только создать, отправить, одобрить руководителем и вернуть. Нужны команды комиссии: отклонение с причиной, возврат на доработку, одобрение к планированию, назначение ответственного/сроков, начало и завершение внедрения, фиксация эффекта/затрат/вознаграждения. Согласовать допустимые переходы, роли и обязательные поля. Фронт не подменяет переходами из HTML реальную бизнес-модель.

| Масштабирование списка | Серверная пагинация, поиск, сортировка, totalCount; сейчас API отдаёт весь список, фронт фильтрует и делит его локально |

## Приоритет 3 — эксплуатация и согласование

- Восстановление пароля: подключить реальный EmailSender и согласовать ссылку письма на `/login?email=...&resetCode=...`; параметры должны быть URL-encoded. Проверить доставку и срок кода. UI не подтверждает фактическую доставку письма.
- Для cookie-аутентификации предпочтителен один HTTPS origin и reverse proxy `/api`. При разных доменах нужны согласованные SameSite/Secure, точный CORS allowlist с credentials и CSRF-защита. Текущий AllowAnyOrigin без allowlist не подходит для cross-origin cookies.
- Проверить CSRF-политику для изменяющих cookie-запросов, особенно до переноса API на другой origin.
- В production убрать фиксированный seed администратора с паролем из `ApplicationDbContextInitialiser`, определить безопасное первичное создание администратора.
- Для конкурентных решений по одному предложению нужен контроль версии (row version/ETag), чтобы не перезаписывать изменения другого администратора.
- Сохранить ProblemDetails для 400/401/403/404/409; договориться об ошибках конкретных полей. Текущий фронт выводит сообщения валидации сервера.
- Проверять TargetDepartmentId и существование подразделения/шаблона на уровне команд; наличие ограничений БД не заменяет понятную валидацию API.
- Предоставить стабильный тестовый API/БД и тестовые аккаунты с каждой ролью. После этого выполнить живые end-to-end проверки. Браузерные тесты фронта с заданными ответами не подтверждают работу реального сервера.
