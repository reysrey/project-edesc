## 1. Роли и текущие возможности

Технические имена Identity сохранены. Соответствие на фронте основано на существующем seed, где главный аккаунт имеет `AdminL1`:

| Роль продукта | Identity | Интерфейс |
| --- | --- | --- |
| Сотрудник | `User` или авторизованный аккаунт без роли | Кабинет, подача идеи, доска; одна реакция «Поддержать» |
| Модератор | `AdminL2` | Входящие, на рассмотрении, на доработке, обработанные; передача в комиссию/возврат |
| Руководитель | `AdminL1` | Обзор, все очереди, эффективность, пользователи, форма, оформление, настройки, экспорт и справочники |

Матрицу нужно закрепить на сервере. Изменение подписей в интерфейсе само по себе прав API не меняет. При наличии обеих ролей фронт выбирает кабинет руководителя.

Уже работают: Identity-вход/регистрация/выход, чтение предложений, создание и отправка идеи, approve/return, CRUD подразделений, создание/изменение/архивирование шаблонов. `/api/Users/me` возвращает `{id,email,fullName,position,departmentId,roles}`. Сборка C# и основной сценарий с настоящим PostgreSQL проверены.

Фронт без изменений API реализует четыре очереди по enum:

- Входящие: `Submitted`.
- На рассмотрении: `InCommission`.
- На доработке: `ReturnedByManager`, `RevisionRequired`.
- Обработанные: `Rejected`, `ApprovedPlanning`, `InImplementation`, `Implemented`.
- Черновики скрыты на доске сотрудника и не входят в четыре очереди модератора. Общий список `/suggestions` фильтрует их только для сотрудника; прямой переход модератора на этот адрес не является границей доступа. Сервер обязан проверять видимость самостоятельно.

Поиск, сортировка, пагинация и экспорт сейчас выполняются клиентом по полученному массиву. CSV содержит только реально доступные поля: ID, название, статус, дата. Невыгружаемые поля отключены. Временный текст формы хранится в sessionStorage этой вкладки под ID пользователя; это не серверный раздел «Мои предложения».

## B01 — P0: подробности, авторство и выборка своих записей

### GET `/api/Suggestions/{id}`

Все операции MVP-01 требуют авторизации. Карточка возвращает `200 OK` с объектом следующей формы.

```typescript
type SuggestionStatus =
  | 'Draft' | 'Submitted' | 'ReturnedByManager' | 'InCommission'
  | 'RevisionRequired' | 'Rejected' | 'ApprovedPlanning'
  | 'InImplementation' | 'Implemented';

type SuggestionAction = 'edit' | 'submit' | 'moderate' | 'commission' | 'support';

type SuggestionDetails = {
  id: string; title: string; status: SuggestionStatus; created: string;
  createdBy: string | null; authorName: string | null; isMine: boolean; isAnonymous: boolean;
  targetDepartmentId: string; departmentName: string | null;
  improvementObject: string; currentFlaws: string; proposedSolution: string;
  templateId: string | null; templateName: string | null; templateIsActive: boolean | null;
  registrationNumber: string | null; commissionNote: string | null;
  allowedActions: SuggestionAction[]; version: string; submissionCount: number;
  supportCount: number; supportedByMe: boolean;
  history: {
    id: string; occurredAt: string; fromStatus: SuggestionStatus;
    toStatus: SuggestionStatus; note: string | null;
  }[];
};
```

Чужой черновик и любая другая невидимая запись возвращают `404`. Поле `commissionNote` доступно автору, руководителю `AdminL1` и модератору `AdminL2` целевого подразделения в видимых им карточках. Остальные читатели получают `null`. `templateName` и `templateIsActive` берутся из справочника, включая архивные шаблоны. Если привязки или записи в справочнике нет, оба поля равны `null`.

| `allowedActions` | Кому и когда доступно | Вызов |
| --- | --- | --- |
| `edit` | Автору в `Draft`, `ReturnedByManager`, `RevisionRequired` | `PUT /api/Suggestions/{id}` |
| `submit` | Автору в `Draft`, `ReturnedByManager`, `RevisionRequired` | `POST /api/Suggestions/{id}/submit` |
| `moderate` | Руководителю или модератору целевого подразделения в `Submitted` | `POST /api/Suggestions/{id}/approve` с `{regNumber}` или `/return` с `{reason}` |
| `commission` | Руководителю или модератору целевого подразделения в `InCommission` | `POST /api/Suggestions/{id}/commission/{decision}` с `{version, note}` |
| `support` | Читателю чужого видимого предложения при включённой поддержке. Доступно для состояний, кроме `Draft` и `Rejected` | `PUT` или `DELETE /api/Suggestions/{id}/support` |

Допустимые решения комиссии — `approve`, `return` и `reject`. Успех возвращает `204`. Для возврата и отклонения требуется причина. При изменившейся версии сервер отвечает `409`. Замечания в истории доступны на тех же условиях, что `commissionNote`. У анонимного предложения для других пользователей `createdBy` и `authorName` равны `null`. Для поддержки действует ограничение в одну реакцию на пользователя и предложение.

### GET `/api/Suggestions/search?scope=mine`

Возвращает `200 OK` со страницей записей текущего пользователя, включая его черновики. Остальные параметры запроса опциональны.

```text
?scope=mine
&search=...
&status=Submitted
&departmentId=<guid>
&from=2026-11-01&to=2026-11-30
&sort=createdDesc|createdAsc|title|status
&pageNumber=1&pageSize=20
```

```typescript
type SuggestionListItem = {
  id: string; title: string; status: SuggestionStatus; created: string;
  createdBy: string | null; authorName: string | null;
  targetDepartmentId: string; departmentName: string | null;
  improvementObject: string; shortDescription: string;
  allowedActions: SuggestionAction[];
  supportCount: number; supportedByMe: boolean;
};

type SuggestionSearchResult = {
  items: SuggestionListItem[]; totalCount: number; pageNumber: number; pageSize: number;
};
```

Поиск проверяет название, проблему и решение. `from` и `to` включают указанный день по UTC. По умолчанию сортировка `createdDesc`, первая страница и 20 записей. Максимальный размер страницы — 100. `totalCount` учитывает видимость, владельца и фильтры. `GET /api/Suggestions` возвращает массив `SuggestionListItem[]`.

## B02 — P0: черновики и повторная подача

### POST `/api/Suggestions/` и PUT `/api/Suggestions/{id}`

Создание принимает `SuggestionInput`. Для сохранения существующей записи дополнительно передаётся `version` из карточки или из последнего ответа PUT.

```typescript
type SuggestionInput = {
  title: string; currentFlaws: string; proposedSolution: string;
  improvementObject: string; targetDepartmentId: string;
  templateId?: string | null;
  isAnonymous?: boolean;
};

type UpdateSuggestionInput = SuggestionInput & { version: string };
type UpdateSuggestionResponse = { version: string };
```

Для создания отправляйте один необязательный заголовок `Idempotency-Key` на попытку, например UUID. Допустимая длина от 1 до 128 символов. Допустимы латинские буквы, цифры и `._~-`. При повторе с тем же ключом и теми же значениями полей тот же пользователь получает `201 Created`, тот же GUID в виде JSON-строки и тот же `Location`. Порядок полей в JSON не влияет на сравнение. Повтор работает и после редактирования исходного черновика или архивации его шаблона. Если значения отличаются, сервер отвечает `409`. Ключи разных пользователей независимы.

PUT сохраняет поля и возвращает `200 OK` с актуальной версией, сохраняя текущий статус. Повторите `templateId` из карточки, чтобы оставить существующую привязку. Для отвязки передайте `null` или опустите поле. Новая привязка при POST или PUT требует активный шаблон. Существующая привязка к архивному шаблону сохраняется при редактировании и подаче.

Название и объект обязательны, до 200 символов. Проблема и решение обязательны, до 10 000 символов. Подразделение должно существовать. Ошибки полей возвращают `400` с объектом `errors`. Для PUT `version` — непрозрачная строка из 64 символов. Устаревшая версия, конкурентная запись или недопустимый статус дают `409`.

### POST `/api/Suggestions/{id}/submit`

Вызов без тела. Автор подаёт `Draft`, `ReturnedByManager` или `RevisionRequired` и получает `204 No Content`. Переход в `Submitted` увеличивает `submissionCount` на единицу. При повторной передаче в комиссию сохраняется исходный регистрационный номер.

Перед отправкой сохраните `submissionCount` из карточки. Если ответ потерялся, снова прочитайте карточку. Рост счётчика подтверждает, что подача произошла, даже если модератор уже успел вернуть ту же запись. Если счётчик прежний, повторить вызов можно при наличии `submit` в актуальном `allowedActions`. Счётчик учитывает подачи с момента применения миграции MVP-01. Для старых записей начальное значение равно нулю.

Для PUT и submit чужой черновик и отсутствующий ID дают `404`, а чужая запись в другом статусе — `403`. Недопустимый или конкурентный переход при submit даёт `409`. Без авторизации сервер отвечает `401`.

## Настройки, реестр и уведомления

- `GET /api/ServiceSettings/` возвращает `supportEnabled`, `anonymousEnabled`, `notificationsEnabled`, `boardEnabled` и `version`. `PUT` с теми же полями доступен руководителю и возвращает сохранённые настройки. При конфликте версии возвращается `409`.
- `GET /api/Users/directory` доступен руководителю. Поддерживает фильтры `search`, `role`, `departmentId` и параметры пагинации `pageNumber`, `pageSize`.
- `GET /api/Users/notifications` возвращает до 20 уведомлений текущего пользователя в порядке от новых к старым. В записи есть `id`, `suggestionId`, `title`, `status` и `occurredAt`.

## B03 — P0: защита действий и пользователей

В текущем коде необходимо исправить:

1. `GetSuggestionsQueryHandler` выбирает все записи без ограничения пользователя — добавить серверную видимость.
2. `SubmitSuggestionCommandHandler` выбирает по ID без проверки владельца — добавить object-level authorization.
3. Approve/return защищены AdminL1/AdminL2, но обработчики не ограничивают подразделение модератора — добавить проверку области ответственности.
4. Update/Delete подразделений и Update/Archive шаблонов имеют только общую авторизацию группы — ограничить руководителем по согласованной матрице. Фронт уже скрывает эти кнопки у модератора и сотрудника.
5. При регистрации назначать User и определить процедуру выбора/назначения подразделения. Сейчас обычная регистрация не присваивает роль и не принимает ФИО.
6. Не полагаться на disabled-кнопки, маршруты фронта или клиентский allowedActions как на защиту.
7. CreateDepartment и CreateTemplate сейчас явно разрешают обе роли AdminL1/AdminL2. Это тоже нужно привести к новой матрице: создание и изменение справочников — руководителю, если команда подтверждает текущее продуктовое разделение.
8. Определить источник подразделений модератора: `ApplicationUser.DepartmentId`, `Department.HeadUserId` или отдельное назначение. Сейчас эти поля существуют, но обработчики approve/return их не используют для проверки прав.

Предлагаемые контракты управления (только руководитель):

```text
GET   /api/Users?search=...&role=...&departmentId=...&pageNumber=1&pageSize=20
PATCH /api/Users/{id}/roles       { roles: ["User"|"AdminL2"|"AdminL1"] }
PATCH /api/Users/{id}/access      { isActive: boolean }
PUT   /api/Users/{id}/profile     { fullName, position, departmentId }
```

Ответ списка: `{items:[{id,email,fullName,position,departmentId,roles,isActive}],totalCount}`. Запретить снятие последнего руководителя и случайную блокировку собственного единственного руководящего аккаунта. Обеспечить реальное прекращение доступа заблокированной сессии.

Для собственного профиля — GET `/api/Users/me` уже есть; добавить разрешённое редактирование ФИО/должности и согласованный порядок изменения подразделения без самостоятельного назначения роли. Смену почты/пароля можно использовать из существующего `/manage/info`, не дублируя Identity. Для выбора модератора в подразделении нужен список пользователей с ID и ФИО; поле `headUserId` уже есть, но сейчас выбирать человека не из чего. На сервере проверять, что выбранный пользователь существует, имеет нужную роль и допустим для подразделения.

Конкретный вариант редактирования своих данных: PUT `/api/Users/me/profile` с `{fullName,position}` → актуальный ответ `/me`. Подразделение и роль назначаются через руководителя либо согласованную процедуру подтверждения. Встроенный `/register` сейчас принимает только email/password: для ФИО из макета понадобится этот отдельный шаг либо расширенный согласованный сценарий регистрации.

**Приёмка:** прямые HTTP-запросы обычного сотрудника к управлению пользователями/справочниками получают 403; модератор не обрабатывает чужое подразделение; UI после повторного входа получает правильные роли из `/me`.

## B04 — P0: полный цикл комиссии и внедрения

Сохранить существующие маршруты `/{id}/approve` с `{regNumber}` и `/{id}/return` с `{reason}` — они работают. В продукте это первичная модерация, технические имена Manager пока не переименовывать без миграции клиента.

Предлагаемые новые операции:

| Маршрут POST | Тело | Переход |
| --- | --- | --- |
| `/api/Suggestions/{id}/commission/return` | `{reason,version}` | InCommission → RevisionRequired |
| `/api/Suggestions/{id}/commission/reject` | `{reason,version}` | InCommission → Rejected |
| `/api/Suggestions/{id}/commission/approve` | `{comment,implementerUserId,implementationDeadline,version}` | InCommission → ApprovedPlanning |
| `/api/Suggestions/{id}/implementation/start` | `{version}` | ApprovedPlanning → InImplementation |
| `/api/Suggestions/{id}/implementation/complete` | `{actualResult,implementationCost,economicEffectAmount,rewardAmount,version}` | InImplementation → Implemented |

Определить права руководителя и назначенного исполнителя, обязательные поля, сроки и допустимые переходы. Не позволять произвольную запись enum через общий update. Комментарий при отказе и доработке обязателен. После каждого действия возвращать обновлённую запись/версию и писать историю. При конфликте версий отдавать 409 с предложением перечитать запись.

Не всё нужно создавать с нуля: в `Suggestion` уже есть `RejectByCommission(reason)`, но HTTP endpoint и команда отсутствуют. Поля исполнителя, сроков и финансов также уже существуют. Поля `actualResult`, истории и версии из предлагаемого контракта сейчас в сущности отсутствуют — для них нужны хранение и миграции. Проверять неотрицательные финансовые значения, согласованные валюту/точность и UTC сроков. RegNumber ограничен столбцом в 200 символов и уникальным индексом: добавить явную валидацию длины и понятную ошибку дубликата.

**Приёмка:** идея проходит путь от подачи до внедрения; невозможно отклонить уже внедрённую или одобрить несоответствующий этап простым HTTP-запросом.

## B05 — P1: одна реакция «Поддержать»

Четыре старые реакции из макета удалены. Нужна ровно одна поддержка от пользователя на предложение:

```text
PUT    /api/Suggestions/{id}/support     // добавить; повтор идемпотентен
DELETE /api/Suggestions/{id}/support     // убрать; повтор идемпотентен
```

Ответ: `{supportCount: number, isSupportedByMe: boolean}`. Добавить оба поля в список и карточку. Уникальный индекс `(SuggestionId,UserId)`, атомарные счётчики, проверка видимости и настройки поддержки. Уточнить возможность поддержки собственного предложения и допустимые статусы. Не раскрывать личности поддержавших без отдельного требования.

**Приёмка:** два клика/повтор запроса не добавляют два голоса; число и состояние восстанавливаются после обновления и видны другому пользователю. Пока этого API нет, кнопка на фронте отключена и не показывает выдуманный нулевой счётчик.

```text
POST   /api/Attachments                  multipart/form-data, file
GET    /api/Attachments/{id}              защищённая выдача файла
DELETE /api/Attachments/{id}              проверка прав/связей
```

Ответ загрузки: `{id,url,fileName,contentType,size}`. Лимит из макета — 5 МБ для фото; проверить MIME, фактическое содержимое и размер на сервере. Разрешённые форматы согласовать (минимум JPEG/PNG/WebP). Удалять потерянные временные загрузки. В detail/list отдавать безопасные URL и alt/тип «до/после». Проверять право прикрепить конкретный файл и настройки анонимности.

**Приёмка:** фото и эффект доступны после повторного входа; отключённая анонимность не обходится запросом напрямую; публичный DTO не выдаёт скрытого автора.

## B07 — P1: история и уведомления

Историю можно включить в GET карточки: `history:[{id,action,fromStatus,toStatus,at,actorName,comment}]`. Не собирать её на клиенте и не создавать фиктивные прошлые события. Фильтровать служебные комментарии по правам.

```text
GET  /api/Notifications?unreadOnly=true&pageNumber=1&pageSize=20
POST /api/Notifications/{id}/read
POST /api/Notifications/read-all
```

Ответ: `{items:[{id,suggestionId,title,text,created,isRead}],unreadCount,totalCount}`. Только свои уведомления; отметка прочитанного сохраняется на сервере. Генерировать события при реальном изменении статуса/комментария и учитывать общую настройку уведомлений.

## B08 — P1: настройки формы, сервиса и оформления

Пока эти экраны на фронте показывают ограничения; оформление имеет только живой предпросмотр. Нет общего сохранения и выдуманных действующих значений.

```text
GET/PUT /api/Settings/service
{ supportEnabled, anonymousEnabled, statusNotificationsEnabled, publicBoardEnabled }

GET/PUT /api/Settings/form
{ hint, fields: { title, category, department, problem, solution, expectedEffect, beforePhoto, afterPhoto, anonymous } }

GET/PUT /api/Settings/branding
{ companyName, brandColor, fontFamily, logoAttachmentId, welcomePatternAttachmentId }
```

GET возвращает авторитетные значения и безопасные значения по умолчанию. PUT только руководителю. Обязательные бизнес-поля нельзя отключать так, чтобы сервер перестал валидировать команду. Изменение формы не должно удалять ранее сохранённые данные. Для логотипа/паттерна использовать файловый API, лимит предпросмотра — 2 МБ. На клиенте не хранить общие настройки компании в localStorage.

**Приёмка:** сохранённые настройки видны в новой сессии и на другом устройстве; сервер соблюдает запреты анонимности/поддержки/публичной доски независимо от клиента.

## B09 — P2: архив, аналитика и экспорт

- Добавить GET `/api/Templates?includeArchived=true` (либо отдельный архив), доступный руководителю. Существующий GET возвращает только активные. Для восстановления можно использовать уже имеющийся PUT с `isActive:true`, когда клиент сможет достоверно получить архивную запись.
- Проверить связи шаблона с подразделением и предложения с шаблоном: поля DepartmentId/TemplateId существуют, но в текущих EF-конфигурациях для этих двух связей не объявлены внешние ключи. Согласовать nullable и поведение при удалении/архивации, добавить валидацию и нужные ограничения миграцией.
- Для эффективности нужны actualResult, затраты, экономия, даты внедрения и измерения. Сейчас фронт считает количество/долю внедрённых по реальным статусам, недоступные метрики показывает прочерком.
- Предлагаемый GET `/api/Analytics?from=...&to=...&departmentId=...`: `{total,implemented,approved,byStatus,byDepartment,implementationCost,economicEffectAmount,rewardAmount}`. Оговорить валюту, период, null и отсутствие данных.
- Для большого объёма данных — серверный CSV endpoint с теми же фильтрами и правами, без ограничения текущей страницей. Экспорт не должен раскрывать закрытые поля/личности анонимных авторов.

## B10 — эксплуатация и проверка готовности

- Подключить EmailSender: forgotPassword/resetPassword уже вызываются фронтом, но реальная доставка не проверена. Ссылка письма — `/login?email=<urlencoded>&resetCode=<urlencoded>`, согласовать кодирование, срок и одноразовость.
- В production использовать один HTTPS origin с прокси `/api`, проверить cookie Secure/SameSite, CSRF и forwarded headers. При отдельных origin нужен точный allowlist CORS с credentials.
- Убрать фиксированный seed-пароль из production; сохранить безопасную процедуру первого руководителя. Названия технических ролей не менять без согласованной миграции.
- Сохранять ProblemDetails: 400 `{errors:{field:[message]}}`, 401, 403, 404, 409 `{detail}`. Не возвращать 200 с ошибкой внутри JSON.
- Разделить причины `DbUpdateException`: сейчас обработчик всегда сообщает «Запись с такими данными уже существует», хотя исключение может означать неверный внешний ключ или запрет удаления связанного подразделения. Отдавать подходящее сообщение/код для каждой ожидаемой ситуации.
- Привести пользовательские сообщения и подписи seed-аккаунта к названиям «Модератор»/«Руководитель». Технические `AdminL1`, `AdminL2`, `ApproveByManager` можно сохранить. Сейчас часть доменных ошибок продолжает называть первичную проверку проверкой руководителя.
- Согласовать способ выдачи корпоративного доступа: свободная регистрация, подтверждение рабочей почты или приглашение. Наличие поля email не обеспечивает связь сотрудника с нужным предприятием/подразделением.
- Покрыть интеграционными тестами права, принадлежность, все переходы, конкурентные изменения и одну поддержку на пользователя. Сейчас в Application.FunctionalTests есть инфраструктура, но тестовые сценарии не обнаруживаются.

## Порядок реализации

1. B01 + B02 + B03 — карточка, свои записи, редактирование и права. Без этого полноценная работа с возвратами невозможна.
2. B04 — завершить весь жизненный цикл идеи.
3. B05 + B06 + B07 — поддержка, фото, эффект, история и уведомления.
4. B08 + B09 + B10 — общие настройки, расширенная аналитика и эксплуатация.

После каждого блока передать актуальный OpenAPI и тестовые аккаунты трёх ролей. Новые маршруты и формы ответов подключать на фронте отдельными изменениями; простое появление endpoint-а не активирует отключённые элементы автоматически.
