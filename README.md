# IdeaHub / KaizenBoard

Внутреннее приложение для предложений по улучшению предприятия. Backend: .NET 10, ASP.NET Core Minimal API, PostgreSQL, Clean Architecture/CQRS. Frontend: React, TypeScript, Vite.

## Локальный запуск

Нужны .NET SDK **10.0.402 или совместимый по global.json** (проверено с 10.0.404), Docker Desktop и Node.js 24 LTS.

Из корня репозитория запустите базу:

```powershell
docker compose up -d
```

В отдельном терминале запустите API:

```powershell
dotnet run --project src/Web --launch-profile http
```

API: http://localhost:5000, документация: http://localhost:5000/scalar. При старте сервер применяет миграции и seed. Seed-администратор предназначен только для локальной разработки; параметры смотрите в ApplicationDbContextInitialiser.cs.

В другом терминале запустите фронтенд:

```powershell
cd frontend
npm ci
npm run dev
```

Приложение: http://127.0.0.1:5173. Запросы `/api` проксируются на `http://localhost:5000`. Браузер должен открывать фронтенд, а не API. Изменить адрес API можно через `frontend/.env` по примеру `.env.example`.

## Структура

- `frontend/src/app` — приложение, маршруты, layout, тема, стили макета.
- `frontend/src/features` — сценарии авторизации, предложений, справочников, аналитики.
- `frontend/src/shared` — типизированный API, runtime-проверка контрактов, общие компоненты и форматирование.
- `src/Domain` — бизнес-сущности и статусы.
- `src/Application` — команды и запросы.
- `src/Infrastructure` — EF Core, PostgreSQL и Identity.
- `src/Web` — HTTP API.
- `tests` — тесты бэкенда; `frontend/e2e` — браузерные тесты фронта.
- `docs/design/ideahub.html` — исходный HTML-макет.

Подробности архитектуры, развёртывания и проверок — в [frontend/README.md](frontend/README.md).

## Границы текущей интеграции

Фронт работает с имеющимися endpoint-ами и добавленным GET `/api/Users/me`. Он не содержит демо-входа или фальшивых записей. Полный сценарий макета требует развития API: подробной карточки, прав владельца, редактирования, комиссии, фото, голосов и уведомлений. Конкретный список для команды — [docs/BACKEND_HANDOFF.md](docs/BACKEND_HANDOFF.md).

Для проверки фронта без запущенного API доступны браузерные тесты с явно заданными ответами. Они не заменяют проверку с реальной БД и сервером.

## Просмотр трёх ролей локально

Откройте http://127.0.0.1:5173, выйдите из текущего аккаунта и войдите нужной учётной записью:

| Кабинет | Почта | Роль Identity |
| --- | --- | --- |
| Сотрудник | `employee@localhost` | `User` |
| Модератор | `moderator@localhost` | `AdminL2` |
| Руководитель | `admin@localhost` | `AdminL1` |

В проверенном локальном окружении у всех трёх пароль `Admin123!` из существующего development seed. Эти данные предназначены только для локальной проверки. Для одновременной работы под разными аккаунтами используйте разные профили браузера: обычные вкладки делят cookie-сессию.

Для повторной подготовки локальных сотрудника и модератора:

```powershell
./scripts/Initialize-LocalRoleAccounts.ps1
```

Скрипт обращается только к localhost и проверяет принадлежность контейнера `kaizenboard-db` проекту `project-edesc`. Новые аккаунты получают пароль из существующего локального seed (либо параметра `-Password`). Пароли существующих аккаунтов не меняются; при несовместимых ролях скрипт останавливается. Роли назначаются только в локальной БД — новые административные HTTP endpoint-ы для этого не добавлялись.

## Завершённые возможности фронта по обновлённому макету

- Названия кабинетов: сотрудник, модератор, руководитель. У сотрудника отдельная доска без административного меню; у модератора четыре очереди; у руководителя полная структура разделов макета.
- Рабочие очереди, их счётчики, поиск по названию/ID, сортировка, 10/20/50/100 записей на странице, фильтры и текущая страница в URL.
- Картотека шести направлений макета плюс реальные шаблоны предприятия. Подсказки/объект/подразделение подставляются в форму из выбранного шаблона.
- Временный текст формы восстанавливается в той же вкладке. После неудачного submit сохраняется ID уже созданной записи; повторная отправка после закрытия/открытия формы не создаёт дубликат.
- CRUD подразделений, создание/изменение/архивирование шаблонов у руководителя; поиск в обоих справочниках.
- Обзор и эффективность на реальных статусах, выбор полей CSV и экспорт всей отфильтрованной очереди, включая все страницы.
- На карточке сотрудника осталась одна кнопка «Поддержать». Пока серверной поддержки нет, она отключена без фиктивного счётчика.
- Разделы пользователей, настройки формы, оформления и сервиса присутствуют. Недоступное сохранение отключено с пояснением. Оформление имеет живой предпросмотр, не меняющий общие настройки.

Серверные пробелы не маскируются демоданными: полный список своих записей, подробности, редактирование, решения комиссии, вложения, поддержка, уведомления и общее сохранение настроек требуют задач B01–B10 из [BACKEND_HANDOFF.md](docs/BACKEND_HANDOFF.md). Новые требования к API в рамках этого этапа не реализовывались.

Проверка обновлённых кабинетов: `npm run check` прошёл (сборка TypeScript/Vite, линтер, форматирование и **30 браузерных проверок** на desktop/mobile). Отдельно без подмены API проверены вход всех трёх локальных аккаунтов, запреты маршрутов интерфейса, отправка идеи сотрудником, возврат модератором AdminL2, новый статус у сотрудника, экспорт выбранной очереди руководителем и выход всех сессий. C#-код на этом этапе не менялся; серверные ограничения из B01–B10 остаются задачами бэкенда.
